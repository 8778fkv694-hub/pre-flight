# 起飞 · Pre-flight

目标：让人的意图在设计、实现、验证和维护中保持连续，产出能用、能验证、能交接的项目。方法结合 The AI-Native SDLC Playbook 与 The New SDLC With Vibe Coding；这里是跨客户端适配方案，不依赖某家模型、命令或专有自动化。

方法来源与跨客户端适配说明见[方法依据](references/method-basis.md)。

## 先确定任务模式

- 用户只要求“理解意图/出方案”：只完成相应文档并等待其反馈，不提前建代码或部署。
- 全新项目：先了解用户与场景，检查目标目录，再创建最小工程资料；技术选型由实际约束决定。
- 已有项目/接续：读现有 AGENT.md、原生入口、STATUS、相关意图与规格，核对代码和未提交改动；复用既有结构，不覆盖式初始化。
- 小修复：在一个工作项里记录意图、修改、验证与恢复即可，不强制六份文档。

只有初始化时读[初始化与客户端适配](references/bootstrap.md)；进入具体阶段时读[六阶段契约](references/workflow.md)对应章节；变更版本/中断/发布时读[变更与恢复](references/change-control.md)；修正基本法条款时读[基本法修正](references/basic-law-change.md)；涉及安全红线、hook或CI检查时读[安全基线与宿主检查](references/safety-baseline.md)，接线到具体平台时读[引导式接线](references/host-wiring.md)。模板位于 assets/project-template/，按需实例化，不把占位符当项目事实。

建立项目基础、调整上下文/工具或从原型转生产时，读[上下文与执行机制](references/context-and-harness.md)。先用人能懂的话协助确立项目目的、原则、边界、自主范围与规则变更方式，再写入 AGENT.md；用户无需先懂工程术语。

## Intent 的确认规则

**人的表达 → AI引导梳理并复述 → 人确认这份复述 → 正式Intent。** 确认前只是原始材料或候选草稿；不能据此施工、冻结Spec或宣称目标已确定。完整过程与示例见[引导式意图确认](references/intent-confirmation.md)，设定或修订Intent时必读。沿用旧确认需有可回查的AI复述及人对该版本的确认；泛化的“继续做”和操作授权不能替代它。

运行中被打断或收到临时补充，不视为对已确认Intent、Spec、Plan或基本法的自动覆盖。先判断类型：澄清 / 操作类指令 / 功能·范围·验收标准变更 / 规则·授权边界变更；混合或判断不清时按更高等级处理，先暂停与补充冲突的动作并保留现场。功能·范围·验收标准变更先转候选Intent，复述变更与影响、人确认后再改依据；规则变更按AGENT.md的“修正程序”处理（细则见[基本法修正](references/basic-law-change.md)）；授权收紧/暂停/撤回立即生效，授权扩大/新增须明确授权并记录。分级与示例见[引导式意图确认](references/intent-confirmation.md)，与在途工作冲突时的处理见[变更与恢复](references/change-control.md)。

## 从人的话到可执行依据

1. 写清为谁解决什么问题、为什么值得做、期望结果、成功标准、范围与非目标。区分用户原话、Agent归纳、假设及未决项。缺少决定性信息时问少量具体问题，能独立调查的继续调查。
2. 将人的输入整理成候选 intent.md，按确认规则引导、复述并请求人确认；确认后才标 accepted。记录复述版本和人的确认依据；实质变更重新走此过程。已确认的同一意图不在各阶段重复确认，操作权限另看既有授权。
3. 写 spec.md：稳定条款ID、行为/数据/权限/界面、边界与反例、独立验收办法。人的目标与做好标准放在前面，工程细节随后。规范中“应实现”与“已验证”分别标识。
4. 写 plan.md：先检查可复用资产，再按依赖拆成可单独演示与恢复的小包，明确文件/状态影响、测试、预算和停止条件。每包映射意图与Spec条款；必要的迭代允许，预算耗尽不换题凑通过。
5. 在授权范围连续实施：先定向验证，再按影响范围回归；界面变更要做真实渲染/交互核验。缺工具或权限如实说明，不能把静态代码检查当页面已验。
6. 审查最终差异与证据，准备交付；发布按实际环境与既有授权执行。交付后将问题与经验回到新意图/工作项和回归样本，未经批准的自动化保持候选。

## 项目资料的真源

- AGENT.md：精简的项目身份、架构入口、真实命令、约束与协作规则；L1条款带[BL-xxx]稳定ID，修正按[基本法修正](references/basic-law-change.md)程序；不堆历史日志。
- STATUS.md：唯一当前进度、已验证身份、施工位置、下一步及阻碍；能指向具体证据。
- intent/spec/plan：分别记录人的目的、决定的要求、落实方法；阶段Plan不等于plan.md文件，文件名按产物含义。
- 验证与交付收据：对应实际源码/包/配置、命令与退出码、样本和未验边界。
- 各客户端入口仅引用AGENT.md；不得产生平行规则副本。现有入口含独立规则时先合并语义，不能直接覆盖。

## V2 批次 A：可选确定性核对

- 基本法新锁覆盖多行受保护条款，旧锁须显式迁移；修正后的重新冻结需要结构化修正记录且差异集合匹配。详情见[基本法修正](references/basic-law-change.md)。
- 项目可运行 `python3 scripts/check_project_contract.py --project . --mode audit` 只读检查 Intent/Spec/Plan 引用和可选测试收据；已有项目默认 audit，不自动改写、不阻断。经项目明确启用后用 `--mode check` 阻断确定性错误。
- 每个工作包最小关联 Spec 版本/条款、Case、实现身份、环境与状态；版本变化后不能沿用旧测试作为新版本已验的证据。

## 执行与证据边界

工件提交是可追溯依据；自动触发下一阶段要有真实配置与验收。没有Git/CI时，用带版本的文件和人工交接明确标注，不能声称有自动门禁。Skill和Markdown是指导，不是权限强制器。

内容冻结、实现验收、正式生效分别记录：冻结设计后可开发；验收绑定精确Spec与实现；交付回读后才报告对应环境生效。候选改版不得提前替换稳定基线或关闭改善事项。

保护他人改动，操作前核对cwd、分支、数据环境。跨Agent按写集合和共享资源安排协作；worktree不隔离HOME、设备、数据库和系统焦点。无并行授权时由当前Agent施工。

有缺陷复现时先保留能抓住原问题的失败证据，再修复；不弱化断言或将所有异常改为跳过。过时测试可带理由修正并复核原控制目标。生成脚本校验实际类型、取值、未知枚举与失败路径，不能只检查字段存在。

生产写入、外发、安装、发布等核对实际授权；保留原操作ID，副作用未知时先只读对账，不换ID盲目重试。任务暂停/取消须区分执行端是否已停止。

## 交付格式

简要说明结果、产物位置、实际验证、未完成与恢复办法。更新STATUS及同一工作包，不用“流程走完”代替业务完成。没有实测的效率收益、客户端兼容性和自动恢复能力均标未验。
