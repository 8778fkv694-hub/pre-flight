# 版本、恢复与接手

工件记录稳定ID、版本、状态、来源与决定依据；引用具体版本，不将latest偷偷带入在途任务。Git提交/PR可承载记录；无Git时用不可变版本副本及变更表，说明保障较弱。无需为普通项目另建工件数据库或流程引擎。

## 变更顺序

人的目标变更 → 更新Intent并记录确定与未决 → 新Spec版本与差异 → Plan调整 → 候选实现 → 验证 → 适用交付批准/执行/回读 → 更新当前有效版本 → 关闭对应改善事项。

Spec可用draft/frozen/superseded；有效版本由STATUS/发布记录指明。实现证据另列planned/implemented/isolated-verified/packaged/installed/business-verified；这组示例按项目裁剪。Intent可用draft/accepted/in-progress/closed/cancelled，取消不等于目标达成。

“接受意图”“冻结设计”“接受实现”“许可部署”是不同决定；同一次明确授权可覆盖多项，记录范围，不制造重复确认。代码变更后旧测试只能证明旧身份，按影响补验证。

## 中断与未知效果

先持久化当前工作、已派发动作与结果，再交接。在途结果未知保持unknown。发布成功但记录失败先回读环境，不盲重发；完成记录只在实际有效版本确认后结案。多目标部分完成逐项列出，不伪称整体完成。

恢复只撤本包可分离变更，保留后来合法工作；数据恢复需核对是否覆盖新数据。旧schema先副本迁移与恢复验证，未知schema只读拒绝不安全覆盖，不自动将旧资料标成已批准。

## 接手最小清单

读入口 → 核对分支/HEAD/未提交 → 对照STATUS及实际运行 → 读取当前包所引Intent/Spec/Plan → 核实旧证据和授权 → 从第一个未完成步骤继续。文档冲突按用户当前明确指令、可回查决定、实际证据裁决；仍有歧义的留明示未决。

每个工作包结束记录：完成/失败/跳过/未验、最终代码和产物身份、命令/环境/输出、资源账、恢复办法及下一步。状态页指向记录，不复制长日志。
