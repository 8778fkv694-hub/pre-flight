# 版本、恢复与接手

工件记录稳定ID、版本、状态、来源与决定依据；引用具体版本，不将latest偷偷带入在途任务。Git提交/PR可承载记录；无Git时用不可变版本副本及变更表，说明保障较弱。无需为普通项目另建工件数据库或流程引擎。

## 变更顺序

人的目标变更 → 新候选Intent → AI复述变更与影响 → 人确认该版本 → 正式纳入并记录未决 → 新Spec版本与差异 → Plan调整 → 候选实现 → 验证 → 适用交付批准/执行/回读 → 更新当前有效版本 → 关闭对应改善事项。

基本法（AGENT.md正文）的修正不并入普通变更顺序：走[基本法修正](basic-law-change.md)程序（提案 → AI复述 → 人明确逐条确认 → 版本与记录 → 修后重验）；L1条款不得以普通实施调整或临时补充直接改写。

Spec可用draft/frozen/superseded；有效版本由STATUS/发布记录指明。实现证据另列planned/implemented/isolated-verified/packaged/installed/business-verified；这组示例按项目裁剪。Intent可用draft/awaiting-confirmation/accepted/in-progress/closed/cancelled，取消不等于目标达成。

“接受意图”必须是人对AI复述的确认；它与“冻结设计”“接受实现”“许可部署”是不同决定；同一次明确授权可覆盖多项，记录范围，不制造重复确认。代码变更后旧测试只能证明旧身份，按影响补验证。

## 中断与未知效果

先持久化当前工作、已派发动作与结果，再交接。运行中被临时补充打断时，先判断类型（澄清 / 操作类指令 / 功能·范围·验收标准变更 / 规则·授权边界变更）；混合型或判断不清时按更高等级处理。与在途工作冲突的补充：先立即暂停与补充冲突的在途动作并保留现场与成果，核对执行端及已派发子Agent确实停止，基线文档暂不改；再按最高类别走候选确认。确认前不继续被叫停的部分，也不开始未确认的新方向；不受影响且已授权的工作可继续。功能·范围·验收标准变更按新候选Intent复述确认；规则变更按[基本法修正](basic-law-change.md)程序处理；授权收紧/暂停/撤回立即生效，扩大/新增须明确授权并记录。在途结果未知保持unknown。发布成功但记录失败先回读环境，不盲重发；完成记录只在实际有效版本确认后结案。多目标部分完成逐项列出，不伪称整体完成。

恢复只撤本包可分离变更，保留后来合法工作；数据恢复需核对是否覆盖新数据。旧schema先副本迁移与恢复验证，未知schema只读拒绝不安全覆盖，不自动将旧资料标成已批准。

## 接手最小清单

读入口 → 核对分支/HEAD/未提交 → 对照STATUS及实际运行 → 读取当前包所引Intent/Spec/Plan → 核实旧证据和授权 → 从第一个未完成步骤继续。文档冲突按用户当前明确指令、可回查决定、实际证据裁决；仍有歧义的留明示未决。

每个工作包结束记录：完成/失败/跳过/未验、最终代码和产物身份、命令/环境/输出、资源账、恢复办法及下一步。状态页指向记录，不复制长日志。
